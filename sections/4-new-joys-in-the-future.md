# 3️⃣
## strategic programming FTW

---

**Tactical programming**

Solving today's problems, picking the best syntax, figuring out the right file structure, "how to name that class?", ...

<br/>
<div class="fragment">

**Strategic programming**

Build code that lasts, design the architecture, think beyond today, "how to name that module?", ...

</div>

note:
[explain the difference between tactical and (slide) strategic programming first]

Leaving the _tactical programming_ to your agents means you can focus on _strategic programming_ entirely.
- *Thinking* about software instead of just *writing* it.
- Adding structure and foresight to your codebase, rather than just solving immediate problems.
- Strategic programming makes for more versatile work, and lets you build experience for future architecture roles.
- Besides: adding a few new features based on the same structure gets repetitive real soon. Some developers prefer to devote their time to solving unique technical challenges.
- To be fair, a lot of people are trying to move from tactical to strategic programming anyway, even if you don't consider the developments in agentic AI, because they want to advance in their career. AI simply accelerates this transition.

note:
We often spend more time reading code than actually writing it, and agentic AI is only increasing that gap.
So improving our code reading skills is becoming increasingly important.
And, as Marit argues in her talk: code reading is indeed a skill.
Because we don't read code like we do text, from start to finish. Code doesn’t run linearly! We scan code to get a feel for the shape, and to find the part we’re interested in.
